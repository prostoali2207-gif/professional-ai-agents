## Diagnosis

A support request is **one persistent object moving through states**, not four things. Four unrelated numbered boxes misrepresent the subject in three observable ways:

1. **Identity loss.** Each box is a separate visual entity, so the viewer never sees that "received" and "resolved" are the same ticket. The core fact of the workflow — continuity of one record — is exactly what the draft deletes.
2. **Causality loss.** Boxes sit in parallel; nothing shows that triage *causes* assignment. The `01→02→03→04` badges are doing sequencing work the object itself should perform, which is the numbered-card default MG3-08 tells me to test before accepting.
3. **Generic visual system.** Four equal cards with number badges reads as presentation UI / dashboard components with no brief-driven reason. Classified `GENERIC_VISUAL_SYSTEM`, not "needs more polish."

## Mechanisms compared (MG3-02)

- **A — Persistent ticket, accumulating state (selected).** One ticket token stays on screen the whole time and travels a single spine. Each transition changes it and *keeps* what came before: arrival stamps the channel, triage adds a category + priority tag, assignment attaches an owner mark, resolution closes it with a seal and the earlier attributes settle into a visible history. Identity, causality and sequence all survive.
- **B — Ownership transfer.** Fixed actor lanes (customer → triage → agent → customer) with the ticket passing between them. Strongest if the brief's real job is accountability/handoff rather than lifecycle. Preserved as a legitimate alternative, not discarded.
- **C — In-place status morph.** Ticket held centre-frame; only its status field and surrounding context change. Best for very short runtime. Weaker at showing progression distance.

I select A, with B kept live for the styleframe review.

## Concrete actions

1. Rebuild the graphic as a single token on a vertical spine (mobile), with the camera travelling with the token so at most two states are on screen at once — four side-by-side zones will not read at phone size.
2. Replace number badges with the state names themselves as the sequencing device. Two type roles only: state name, and attribute chips. No outline/shadow/italic "fixes" (MG3-06).
3. Per element, define `job → represented change → viewer inference → timing/hold → removal criterion` (MG3-09). Transitions get authored easing with a real hold on each state for comprehension; the accumulated attributes persist rather than re-animating, so attention load stays flat.
4. **Truth boundary:** no durations, SLA times, queue volumes, percentages or bar/arc lengths implying measured throughput unless approved evidence exists. The spine is conceptual and must not encode unsupported magnitude (MG-02 / MG3-08).
5. Build the overlay ledger before render: each of the four state labels maps to `approved statement/source beat → time range → owner`. I need the client's actual product vocabulary confirmed — if the product says "in review" rather than "triaged," the label follows the product, and that comes from the brief owner, not from me.
6. Styleframes at opening / peak (mid-transition, attributes visible) / resolved state, plus one ~3s prototype of the real motion language, before any full-length authoring (MG3-13).
7. Runtime route check: a travelling token with persistent attribute marks needs authored vector assets, not CSS cards. If the authoring surface can't carry them, I choose a deliberately simpler direction — I do not silently collapse back into boxes (MG3-14).
